DayKeeper: what the database holds, and when each part of it is written

Ten tables. The five steps along the top are one letter's whole life, from the photograph to the reminder being switched off. Each table's badge says which of those steps writes it. Step four writes nothing at all: the calendar is drawn entirely from rows that are already there. The definition this drawing follows is db/schema.sql, which is the only definition there is.

STEP 1
Photograph and upload
POST /api/documents
STEP 2
The reading
GET /api/documents/:id  (polled)
STEP 3
Check and confirm
POST /api/documents/:id/confirm
STEP 4  ·  READS ONLY
The calendar
GET /api/tasks
STEP 5
Ticking it off
POST /api/tasks/:id/complete

users

  • id
  • email
  • display_name
  • password_hash
  • role
  • timezone
  • deactivated_at
The timezone is why “9 am” means anything. Every date in this system is a calendar day in somebody's zone, never a bare timestamp.

sessions

  • id
  • user_id → users
  • token_hash
  • expires_at
A session is a row, not a signed cookie, so signing out ends it everywhere and a leaked database hands over no live sessions.

documents13

  • id
  • user_id → users
  • status
  • issuer
  • document_type
  • due_date
  • due_time
  • amount_text
  • reference
  • confirmed_at
One letter, whatever its page count.

document_pages1

  • id
  • document_id → documents
  • attempt
  • page_number
  • storage_path
One photographed sheet. Retaking a letter adds a new attempt rather than overwriting the old photographs, because the failed reading was judged against those.

extraction_runs2

  • id
  • document_id → documents
  • attempt
  • status
  • provider
  • model
  • failure_kind
  • raw_response
One attempt at reading, failures included.

extracted_fields23

  • id
  • extraction_run_id
  • field_key
  • extracted_value
  • raw_text
  • status
  • confidence
  • corrected_value
Two columns, not one. What the model read stays; what the person typed instead sits beside it. Overwriting would destroy the only evidence of how often the reader is wrong.

tasks35

  • id
  • user_id → users
  • document_id → documents
  • title
  • issuer
  • due_date
  • due_time
  • state
  • completed_at
Three weeks later, this link answers “what said so?”

reminders35

  • id
  • task_id → tasks
  • scheduled_for
  • channel
  • status
  • sent_at
Rows, not a rule evaluated when somebody looks. Each one can be sent, cancelled the moment the task is ticked off, or fail to send, and a rule cannot remember any of that.

audit_logs

  • actor_id → users
  • action
  • target_type
  • target_id
  • detail
The admin dashboard promises an operator never sees the contents of a letter. This table is how that promise is kept and shown: it records who did what to which record, and has nowhere to put the contents of anything.

ai_prompt_logs

  • extraction_run_id
  • provider
  • model
  • prompt
  • prompt_tokens
Every prompt sent to a model, for the GenAI declaration and for repeating an accuracy claim later.
