DayKeeper: what the database holds, and when each part of it is written

Fourteen tables. The five steps along the top are one letter's whole life, from the photograph to the reminder being switched off. The ten tables on that path carry a badge saying which steps write them; the four below sit off it. Step four has no badge anywhere, because the calendar writes nothing at all: it is drawn entirely from rows that are already there. The definition this drawing follows is db/schema.sql, which is the only definition there is.

STEP 1
Photograph and upload
POST /api/documents → a batch
STEP 2
Divide, read, place
GET /api/home  (polled)
STEP 3
Check and confirm
POST /api/documents/:id/confirm
STEP 4  ·  READS ONLY
The calendar
GET /api/tasks
STEP 5
Ticking it off
POST /api/tasks/:id/complete

upload_batches1

  • id
  • user_id → users
  • status
  • created_at
  • grouped_at
What actually arrived. A person clearing a week of post does not pause to say where one letter ends, so this is the unit, and the letters are worked out afterwards.

upload_pages1

  • id
  • batch_id → batches
  • position
  • storage_path
  • mime_type
One photograph. position is its name, not its meaning: one letter's pages can arrive shuffled between another's, and the order says nothing about who owns what.

grouping_runs2

  • id
  • batch_id → batches
  • attempt
  • status
  • provider
  • model
  • document_count
  • not_letter_count
  • raw_response
The manifest: which photographs are each letter, and which are no letter at all. No screen asks a person to confirm it, so this row is the only thing its accuracy can ever be measured against.

matching_runs2

  • id
  • document_id → documents
  • status
  • provider
  • model
  • matched_document_id
  • tool_calls
Is this the rest of a letter we already have? The reading searches for itself, and this keeps the searches it ran. A pattern and a hit count can be read and argued with; a similarity score cannot.

documents23

  • id
  • user_id → users
  • status
  • issuer
  • document_type
  • due_date
  • due_time
  • amount_text
  • reference
  • provisional_label
  • summary
  • open_payload
  • confirmed_at
One letter, however many sheets.

document_pages2

  • id
  • document_id → documents
  • upload_page_id
  • attempt
  • page_number
  • storage_path
The photographs this letter turned out to own. The link back to the upload keeps "which pile did this come from, and what else came with it" answerable months later.

extraction_runs2

  • id
  • document_id → documents
  • attempt
  • status
  • provider
  • model
  • contract_version
  • raw_response
One attempt at reading one letter, failures included.

extracted_fields23

  • id
  • extraction_run_id
  • field_key
  • extracted_value
  • raw_text
  • status
  • confidence
  • corrected_value
  • corrected_at
  • acknowledged_at
What the model read stays; what the person typed sits beside it, never on top. The third stamp is what makes "never from a date you haven't checked" checkable.

tasks35

  • id
  • user_id → users
  • document_id
  • title
  • issuer
  • due_date
  • due_time
  • state
  • completed_at
Three weeks later, that link answers “what said so?”

reminders35

  • id
  • task_id → tasks
  • scheduled_for
  • channel
  • status
  • sent_at
Rows, not a rule evaluated when somebody looks. Each one can be sent, cancelled the moment the task is ticked off, or fail to send, and a rule cannot remember any of that.

users

  • id
  • email
  • display_name
  • password_hash
  • role
  • timezone
The timezone is why “9 am” means anything. Every date here is a calendar day in somebody's zone.

sessions

  • id
  • user_id → users
  • token_hash
  • expires_at

audit_logs

  • actor_id → users
  • action
  • target_type
  • target_id
  • detail
Never letter content.

ai_prompt_logs
